## Неподвижные правила продукта

- Глобально только «Мысли / Профиль»; внутри мысли только «Дубли / Диалог / Сценарий».
- Статусы только «Не завершена / В работе / Успешно завершена».
- Запись начинается только после явного «Начать запись».
- Финальный дубль и финальный сценарий выбираются независимо.
- AI автоматически сравнивает дубли; ручного A/B-интерфейса нет.
- Во время записи нет AI-диалога; сценарий крупный, stage компактная.
- Голосовой ответ в композере — не запись дубля.
- Мысль можно создать без заполненного профиля.
- Профиль применяется только после подтверждения; незавершённое дополнение не заменяет активный портрет.
- Запись без сценария разрешена. Возможный `SCRIPT_REQUIRED` исследуется и устраняется на медиа-этапе; правило UI молча не меняется.
- Полезные backend/data/API-механизмы сохраняются; UI заменяется постепенно.
- Старые экраны скрываются/перенаправляются только после покрытия действия, сохранения, ошибки и возврата.
- Не добавлять регистрацию, оплату, команды, social publishing и embedded camera без отдельного решения. База: голос + upload подготовленного видео.
- Не ухудшать доступность и адаптивность до финальной полировки.

## Предварительные условия

1. Cursor открыт на корне репозитория Vocal (рабочий код в `src/`).
2. Канонические документы читаются по путям из `docs/design/README.md`.
3. Сервисы, БД и провайдеры настроены по документации репозитория. Секреты в промпты/отчёты не копировать.
4. Команды определять только после просмотра `package.json`, lock-файлов и README.
5. Перед изменением данных иметь безопасный backup/rollback, если он нужен текущей архитектуре.

## Как использовать промпты

1. Открыть numbered-файл и вставить в Cursor только блок «Промпт для Cursor».
2. Выполнять один этап за раз; не продолжать следующий автоматически.
3. В начале сверить текущий код и канон: план описывает результат, но не выдумывает структуру repo.
4. Проверить diff, тесты, ручные сценарии и критерии файла.
5. Записать статус, commit/hash (только если коммит отдельно запрошен), блокеры и решение здесь и в `CHECKLIST.md`.

## Дисциплина изменений, отката и коммитов

- Один этап — небольшой связный diff; в этапе 09 каждая R-подфаза — отдельный checkpoint.
- Не переписывать рабочий backend ради нового вида.
- Не смешивать общий reformat, upgrades и продуктовый этап.
- Миграции обратно совместимы либо имеют проверенный rollback; данные не удалять без отдельного подтверждения.
- Cursor не делает commit/push без прямой команды. Перед коммитом просмотреть staged/unstaged diff.
- Откатывать только текущий этап; не использовать разрушительные git-команды без явного запроса.
- Pre-existing failures фиксировать отдельно, не маскировать и не расширять scope ради случайного ремонта.

## Общее определение готовности

Этап готов, когда выполнены его критерии, сохранены правила данных, покрыты loading/empty/error/success где применимо, нет новых failures tests/lint/build, проверены keyboard и целевые ширины, а handoff перечисляет файлы, проверки, ограничения и rollback. Затем статус остаётся «На проверке» до ручного принятия.

## Проверка после каждого этапа

После завершения любого этапа (00–10) результат обязательно передаётся на проверку агенту **«Создание приложение»** (этот чат Grok Bot), а не сразу в следующий этап.

Как сдавать шаг:
1. Кратко опиши, что сделано (PR / ветка / список файлов).
2. Приложи скриншоты ключевых экранов этапа (desktop и mobile, если менялся UI).
3. Укажи известные блокеры и что сознательно отложено.
4. Дождись вердикта проверки: **принято / правки / стоп**.

Что проверяет агент:
- границы этапа (не расползся ли scope);
- продуктовые правила из README (навигация, статусы, запись, итоги, профиль);
- критерии приёмки из файла этапа;
- регрессии shell / a11y / очевидные UX-дыры;
- готовность к следующему этапу.

Визуальный polish до этапа 10 не блокирует приёмку, если композиция и поведение этапа верны. Без явного «принято» следующий этап не начинать.
