# Флак «two executors of one turnKey call complete once» (v03-agent-actions)

Дата: 15.10.2026. Только разбор; код не менялся, исправление ждёт «да» владельца. Токены модели не тратились (мок `complete`).

## Что падает

`tests/v03-agent-actions.test.ts`, тест «two executors of one turnKey call complete once»: два `runDialogueTurn` с одним `idempotencyKey` параллельно, ожидается ровно один вызов модели (`completeCalls === 1`); падает `actual: 2`.

## Частота

| Условие | Прогонов | Падений |
| --- | --- | --- |
| один тест отдельно (`--test-name-pattern`), машина свободна | 50 | 0 |
| то же, при двух занятых CPU-циклах на 2 ядрах | 50 | 1 |
| то же, с зондом (стек каждого вызова `complete`) | 84 | 1 |
| итого под нагрузкой | 134 | 2 (≈1,5 %) |

В полном наборе падение видели один раз; в изоляции без нагрузки не воспроизводится. Значит, исполнение зависит от тайминга, но тайминг — это окно настоящей гонки в коде, а не ошибка теста.

## Причина (подтверждена стеком)

Зонд печатает стек каждого вызова `complete`. В упавшем прогоне:

1. `complete#1` — `gatewayComplete` из `runDialogueTurn` (`src/lib/dialogue.ts:1669`): исполнитель-лидер, взявший аренду `claimDialogueModelExecution`. Аренда сделана верно: один атомарный `UPDATE … WHERE responseText IS NULL AND (execLeaseUntil IS NULL OR execLeaseUntil <= now)`.
2. `complete#2` — `gatewayComplete` из **`varyRepeatedQuestion`** (`src/lib/dialogue.ts:899`, вызов на 1753), у второго исполнителя (ведомого).

Последовательность: ведомый ждёт в `waitForDialogueModelResponse`, получает `responseText` сразу после записи лидером и идёт по общей постобработке (разбор ответа, `dropDuplicateFact`, `downgradeInvalidReply`, `varyRepeatedQuestion`). Лидер к этому моменту успевает закоммитить ход: вопрос «Один ответ модели» уже в переписке. `varyRepeatedQuestion` читает последние вопросы ассистента (`status: "done"`), находит там **тот же вопрос из этого же хода**, считает его повтором и делает ещё один вызов модели (`REPEAT_QUESTION_NOTE`). Проверки `isDialogueTurnComplete` стоят до постобработки, но не внутри неё, поэтому окно остаётся.

## Последствия в продукте (не только в тесте)

- Лишний платный вызов модели при двойной отправке одного хода (повтор запроса клиента, две вкладки). Частота низкая, но это ровно тот сценарий, ради которого ключ хода существует.
- `varyRepeatedQuestion` при успехе делает `aiCall.update({ responseText: again.text })` (строка 907): у ведомого может **перезаписаться сохранённый ответ модели** уже закоммиченного хода. Сообщение в переписке не дублируется (коммит идемпотентен по `claimKey`), но запись `AiCall` расходится с тем, что показано автору.

## Предлагаемое исправление (не применено)

1. Минимальное и достаточное: в `varyRepeatedQuestion` (и симметрично в `dropDuplicateFact`) исключать из «недавних» сообщения с `claimKey` этого же хода (`where: { claimKey: { not: turnClaimKey(thread.id, key) } }`) — сообщение собственного хода не может быть «повтором» самого себя. Нужен проброс ключа хода в функцию.
2. Дополнительно: повторная проверка `isDialogueTurnComplete` непосредственно перед любым повторным вызовом модели в постобработке (`varyRepeatedQuestion`, `parseReplyRegeneratingInvalidQuestion`, `authorSafeReply`), чтобы ведомый не тратил вызов после коммита лидера.
3. Тест менять не нужно: он правильно ловит дефект. После исправления прогнать этот тест 100 раз под нагрузкой (скрипт — в протоколе), плюс v01+v02+v03.

Изменение трогает `src/lib/dialogue.ts` (ядро принятого V03), поэтому по правилу владельца — только после явного «да».
