## Живое измерение (разрешено владельцем: три диалога под лимитом шлюза)

Условия: модель `openai/gpt-oss-120b` (Groq) через шлюз S1, локальная тестовая БД (live Supabase не затрагивался), ключ из `.env` не читался и не выводился, суточный лимит шлюза включён. Три мысли по 4 хода (первый «уточни» + три ответа автора), диагностика на каждой, затем одна сборка сценария. Скриптом `scripts/r-live/measure.ts` и `scripts/r-live/assemble.ts`.

Примечание: в первом прогоне клиент приложения создался раньше переключения схемы, и данные ушли в схему `public` локальной тестовой БД (не live); скрипт исправлен (`resetPrismaClient`). Числа ниже взяты из `AiCall` этой схемы. В локальной тестовой БД остались 3 мысли измерения.

| Вызов | Количество | Среднее `promptTokens` | Среднее `completionTokens` | Всего на вызов |
|---|---|---|---|---|
| Диагностика дубля (`take-diagnosis`) | 3 | 472 | 393 | ≈ 865 |
| Ход диалога, ответ принят | 7 | 1012 | 371 | ≈ 1383 |
| Ход диалога, ответ модели отвергнут проверкой | 6 | 1256 | 705 | ≈ 1961 |
| Сборка сценария (`script`) | 3 | 373 | 508 | ≈ 881 |
| Все вызовы диалога вместе | 13 | 1124 | 525 | ≈ 1650 |

Всего за измерение ≈ 25,5 тыс. входных+выходных токенов диалога и диагностики и ≈ 2,6 тыс. на три сборки (суточный лимит 200 000).

### Что показало измерение

1. **Из 12 ходов 5 завершились ошибкой (≈ 42 %)**: 2 × `ACTION_GAP` («Нельзя закрыть пробел без принятого факта»), 3 × `AGENT_ACTION_INVALID` («недопустимое обновление состояния»). В S5 было 1 из 4. Выборка маленькая, но вероятная связь с R2: при наличии типизированных пробелов модель чаще пытается закрыть их без принятого факта. Ещё один вызов получил `429` от Groq (лимит токенов в минуту) — для R5 нужен темп.
2. **Дефект R2, исправленный по ходу:** открытые типизированные пробелы блокировали сборку (`NOT_READY`) по правилу V05, и в первом прогоне ни одна сценарий не собрался. Теперь блокируют только пробелы без типа (старые и от исправления автора). После исправления сборка на живой модели: 3 из 3, «что изменено» приходит (3, 1, 1 фраза), текст 87–99 символов.
3. Качество вопросов и сценария не оценивалось (это R5).

### Предложение бюджета R5 (число назовёт владелец)

Расход на один диалог из 6 ходов с диагностикой и двумя сборками: 6 × 1650 + 865 + 2 × 881 ≈ 12,5 тыс. токенов. Для двух вариантов («с карточками» и «без») при N диалогов: `N × 12,5 тыс. × 2 × 1,2 (запас)`. N = 8: ≈ 240 тыс.; N = 10: ≈ 300 тыс. Это выше суточного лимита 200 тыс., значит либо разнести на два дня, либо временно поднять лимит. Нужна пауза между ходами из-за `429`.

Условие до запуска: решение по пункту 1 («что делать с 42 % отвергнутых ходов»). Варианты (решение за владельцем): повтор одного хода при `AGENT_ACTION_INVALID`/`ACTION_GAP`; игнорировать `closeGapIds` без факта вместо ошибки хода; ничего не менять и измерить на большей выборке.

## Предложения без изменения кода

- **Примеры C00 JSON в каждом ходе.** Измерение: весь «Валидный пример вопроса» занимает ≈ 277 символов из ≈ 2850 в запросе (≈ 90 токенов); примеры `wrong_speaker` и `author_negation` и так добавляются только при одном исходном факте. Основной объём — статичный блок правил (≈ 2460 символов, ≈ 800 токенов) в каждом ходе. Не менял: принятый live-тест `c00-live-model` проверяет наличие примера, а выигрыш мал. Возможный путь: вынести статичные правила в системное сообщение для кэша провайдера — это меняет принятый системный промпт V03, нужно решение.
- Показ основы автору: вместе с кнопкой «Сгенерировать сценарий» (R4 UI), решение владельца уже принято, UI не сделан.
