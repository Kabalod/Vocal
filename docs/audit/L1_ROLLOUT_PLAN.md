## 4. Суточные лимиты для тестеров

Что на самом деле ограничивает расход при `VOCAL_QUOTA` off: **только** `VOCAL_DAILY_TOKEN_LIMIT` (на человека) и `VOCAL_DAILY_STT_SECONDS`. Лимит аккаунта Groq — 200 000 токенов в сутки на всех; глобальный выключатель и потолок на мысль **выключены** вместе с квотой (находка 4).

Расчёт для N тестеров, запас 20 % на провайдера и собственные проверки владельца:

| N тестеров | `VOCAL_DAILY_TOKEN_LIMIT` на человека (≈ 160 000 / N) |
|---|---|
| 2 | 80 000 |
| 3 | 53 000 |
| 5 | 32 000 |

Что это даёт: расход одной мысли с диалогом и сценарием **не измерен** (в отчётах есть только суммарные прогоны; потолок J1 для диалога на одну мысль — ≈40 тыс. токенов, это верхняя граница, а не среднее). Если брать потолок 40 тыс., то на аккаунт в сутки помещаются **≈4–5 мыслей в целом**, не на человека. Поэтому: либо поднимать лимит у провайдера (платный тариф исключён), либо ограничивать темп (пустой отчёт покажет реальные цифры в первые 1–2 дня), либо добавить второй ключ/провайдера — вне плана.

Варианты защиты (нужно решение владельца, раздел 9):
- **А (без кода):** только `VOCAL_DAILY_TOKEN_LIMIT` по таблице + ручной контроль отчётом раз в день.
- **Б (маленькое изменение кода, тесты на моках):** отдельный флаг, например `VOCAL_ABUSE_GUARDS=on`, включающий лимит запросов в минуту, глобальный выключатель (`VOCAL_GLOBAL_DAILY_TOKEN_CAP`, задать ≈ 160 000) и потолок на мысль **без** квоты мыслей. Тогда один тестер не может исчерпать сутки всем; миграция не нужна.
- **В:** включить `VOCAL_QUOTA=on` — **нельзя** без миграции 11 (находка 2), поэтому не рассматривается до этапа «ресурс».

Рекомендация: **Б + значения из таблицы**. Без Б один тестер, у которого `VOCAL_DAILY_TOKEN_LIMIT` окажется выше доли, выбирает сутки остальным.

## 5. Учёт расхода по типу действия

Что есть без изменений: `npm run report:ai` (`scripts/ai-usage-report.ts`, `src/lib/ai/usage-report.ts`) — группировка день × контекст (мысль/профиль) × `kind` × `model`: число вызовов, токены запроса/ответа, итого. `GET /api/health` показывает `groq` (есть ли ключ), но не расход.

Чего не хватает (без миграции, только скрипт и отчёт):
1. **По пользователю:** добавить `ownerUserId` (или короткий хэш) в строки и итог «пользователь × день».
2. **Итог за сутки против лимита провайдера** (200 000) и против лимита на человека — одной строкой.
3. **Статусы:** отдельно `done`, `error`, `queued` (сейчас токены суммируются по всем статусам; лимиты считают только `done`/`error`).
4. **STT отдельно:** секунды (`kind = stt`) не смешивать с токенами.
5. **Цена:** оценка себестоимости по токенам — константы тарифа задаёт владелец (в коде нет); понадобится для этапа «ресурс» ($6 за 30 дней).
6. **Список `kind`:** снять из базы (`SELECT DISTINCT kind FROM "AiCall"`), в коде видны `dialogue`, `script`, `from_take`, `compare`, `stt` и др.; в отчёте нужен словарь «kind → человеческое название действия».
7. Опционально (код): одна структурированная строка лога на вызов шлюза (`kind`, токены, `ownerUserId`, статус, длительность) без `promptText`/`responseText`; поле `promptText` остаётся в базе «для повторения», логи его не печатают (`R8`).

Размер: отчёт по пп. 1–6 — ≈ полдня, без миграций и вызова модели; п. 7 — по решению.
