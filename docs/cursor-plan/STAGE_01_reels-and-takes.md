## Порядок работы по файлам

### 1. `prisma/schema.prisma`

Добавь Reel и Take и связь с Job. На переходный период допустима nullable-связь для безопасного backfill.

### 2. `prisma/migrations/<migration>/migration.sql`

Подготовь миграцию без очистки пользовательской БД. Если БД раньше создана через db push, сначала выполни корректный baseline.

### 3. `scripts/backfill-reels.ts`

Для каждой старой Job без дубля создай Reel и Take №1, затем свяжи их транзакционно. Повторный запуск безопасен.

### 4. `src/types/reel.ts`

Добавь DTO и допустимые статусы, различай ReelStatus и JobStatus.

### 5. `src/lib/reels.ts`

Создание, получение, обновление карточек и создание дубля. Нумерация защищена уникальным ограничением внутри Reel.

### 6. `src/lib/serialize.ts`

Добавь новые DTO без раскрытия локальных путей к медиа и сохрани старые контракты.

### 7. `tests/reels-migration.test.ts`

На временной БД проверь сохранность старых связей, повтор backfill и создание дублей.

### Минимальные данные

Reel: id, title, initialNote, status, createdAt, updatedAt. Назначение и
аудиторию можно добавить сейчас или этапом анкеты. Предусмотри явный выбор
финального дубля с проверкой его принадлежности карточке.

Take: id, reelId, number, inputType (video/audio/text), authorNote, createdAt.
Связь Job с Take позволяет впоследствии иметь несколько технических запусков
для одной записи. Текстовую попытку можно создавать без видео и без Job.

Старые AnalysisResult остаются связаны с прежними Job. Не меняй их payload
при переносе. Не объединяй разные старые загрузки в одну идею по догадке.
Архивирование карточки не удаляет её содержимое.

Повторное создание дубля при двойной отправке одного запроса нужно отличать
от сознательной загрузки того же файла как нового дубля: используй ключ
повтора запроса, а не запрет одинаковых файлов.
