Работа ведётся последовательно: принятая база → изменения данных/API/UI → проверка → отчёт → внешнее ревью. После каждого этапа остановиться до принятия; не реализовывать весь план одним изменением.

## 1. Продуктовые решения, имеющие приоритет

1. Пользователь ничего не подтверждает и не исключает для обучения профиля. Не создавать очередь пользовательского одобрения, кнопки «Запомнить», «Принять профиль» или обязательные уточнения ради ведения памяти.
2. Система автоматически выбирает, что сохранить, обновить, оставить локальным, отложить или не запоминать.
3. Память минимальная: хранить значимое для вопросов, сценариев и ограничений использования материала. Не строить психологический портрет.
4. Нет fine-tuning весов модели, карты прогресса, баллов качества автора и графиков развития навыков.
5. Сохраняются сообщения, версии, дубли и исторические снимки. Производная память не переписывает источники.
6. Модель вызывается по явному действию: отправка сообщения, голосового ответа, запрос сценария/разбора. Просмотр страницы, фильтры и сохранение черновика модель не запускают.
7. Автообработка памяти может быть частью операции, начатой явной отправкой. Она учитывается в общем расходе и лимите, не является бесконечным фоновым процессом.
8. Мысль можно создать без анкеты. Анкета — адаптивный разговор, один смысл за ход, без обязательного числа вопросов.
9. Готовый дизайн сохраняется. Диалог не появляется в дублях. Три пользовательских статуса мысли не меняются. «Черновик» относится к сценарию.
10. Автоматическая память не означает автоматическое разрешение использовать личные факты в сценариях. understanding/in_text сохраняются; вес не расширяет разрешения.
11. Обучение относится только к текущему владельцу. Данные других пользователей и корпус блогеров не становятся его биографией.

### Замена старых правил

| Старое положение | Новое решение |
| --- | --- |
| Ревизия портрета только после подтверждения | Автоматическая ревизия при значимом обоснованном изменении |
| Нет отдельного хранения сигналов обучения | Есть компактная память, источники и журнал решений |
| Один local-автор | Пользовательская изоляция на принятой Supabase/Auth-базе |
| Старый портрет навсегда задаёт будущие действия мысли | Исторические снимки неизменны; каждый новый вызов собирает новый снимок с приоритетом локальных решений |

Прежнее требование явного подтверждения профиля отменено этой инструкцией. Оно не должно возвращаться из старых документов или тестов. При этом требования ревью разработки сохраняются.

## 3. Целевая архитектура

Поток одной операции:

1. Авторизация, ownership, idempotency key, фиксация сообщения и версии входа.
2. Режим определяется сервером по действию/диалогу; модель классифицирует намерение внутри режима.
3. Анализатор извлекает позицию, материал, пробелы и кандидатов памяти со ссылками на источники.
4. Код проверяет контракт, происхождение и допустимость извлечений.
5. Транзакционно обновляются состояние мысли и допустимая память с проверкой версий.
6. Сборщик выбирает применимую память и паттерны, создаёт неизменяемый снимок ответа.
7. Генератор формулирует разрешённое действие: один вопрос, объяснение, предложение сценария или возврат к задаче.
8. Код проверяет и сохраняет результат; интерфейс показывает его в существующем диалоге.

Логические модули: operation handler, answer analyzer, memory policy, thought state reducer, context builder, craft selector, response generator, result validator. Это не восемь отдельных LLM-вызовов. Начальный бюджет — до двух логических вызовов: анализ и формулировка, плюс максимум один ограниченный repair при невалидном ответе. Все попытки видны в учёте. Для простого off-topic ответа использовать шаблон без второй генерации.

Сохранение сообщения — отдельная надёжная граница. Ошибка анализа не теряет ответ. Ошибка генерации после обновления памяти не применяет память повторно при retry. Невалидный анализ не меняет рабочий профиль.

## 4. Данные: логические контракты

Имена ниже проектные. В I00 сопоставить с фактической схемой, избегая дублирования существующих сущностей.

### AuthorMemory

- id, userId, canonicalKey, category, value, scope;
- evidenceType: direct_statement / explicit_preference / behavioral_observation / legacy_profile;
- confidence, significance, status: candidate / active / disputed / superseded / expired / suppressed;
- usage: understanding / in_text, ограничения области использования;
- validFrom/validTo для предметной актуальности, firstObservedAt/lastObservedAt;
- revision, policyVersion, supersedesId при необходимости.

Категории: цель, аудитория по умолчанию, текущая деятельность, прошлый опыт, темы, стиль, способ диалога. Ограничения использования — отдельно учитываемый обязательный набор, не вытесняемый обычным рейтингом предпочтений.

### MemoryEvidence

- userId, memoryId, sourceType/sourceId/sourceVersion, точный фрагмент или диапазон;
- relation: supports / contradicts / corrects;
- independenceKey, operationId, extractorVersion;
- происхождение: авторская речь / цитата / гипотеза / сгенерированный текст.

Уникальность свидетельства не позволяет повторному вызову, перефразированию или новой версии extractor автоматически увеличить вес того же источника. Проверять владельца источника и принадлежность разрешённому контексту.

### MemoryUpdate

Внутренний журнал автоматических решений: operationId, sourceWatermark, before/after или ссылки на версии, action, reasonCode, policyVersion. Это не пользовательская очередь подтверждений. Исключить секреты и полный текст переписки из обычных логов.

### ThoughtState

userId, reelId, revision, sourceWatermark, contentMode, intent, position, evidenceRefs, audienceOverride, openGaps, decisions, rejectedSuggestions и локальные ограничения. Структурированные элементы имеют источники. Хранить состояние ограниченным по объёму; полная история остаётся в существующих сущностях.

### Существующие сущности

- ProfileRevision: неизменяемая совместимая проекция памяти в восемь полей портрета; currentRevisionId меняется атомарно. Инициализация и обновление без подтверждения.
- ReelContextSnapshot/AiCall: расширить версиями памяти, ThoughtState, prompt/policy/extractor, паттернов и перечнем источников. Snapshot содержит использованные значения, а не только ссылки на изменяемые строки.
- Question/DialogueMessage: использовать для цели вопроса, связанного пробела и результата, если схема позволяет. Не создавать вторую историю вопросов без необходимости.
- Ручные правки и finalTakeId/finalScriptId: исходные сигналы, не автоматическое доказательство предпочтений.

Исторические снимки не редактируются обычным обучением. Запрос удаления данных — отдельное исключение: нельзя оставлять удалённые персональные сведения навечно в снимках под предлогом неизменяемости. Предусмотреть каскад/редакцию производных данных и запрет повторного извлечения удалённой памяти.

## 5. Политика минимальной памяти v1

### Сначала обязательные фильтры

- Чужая цитата, условный пример, инструкция из корпуса и текст ассистента не становятся фактом автора.
- Явное указание «в этом ролике» остаётся в ThoughtState.
- Неоднозначное противоречие переводит спорное сведение в disputed; система не спрашивает ради памяти и не использует его как установленный факт.
- Прямое исправление имеет приоритет над накопленными повторами. Прошлый опыт сохраняется как прошлый.
- Не извлекать диагнозы, скрытые мотивы, политические/религиозные и другие чувствительные характеристики из косвенных признаков.
- usage не повышается из-за достоверности, частоты или итогового выбора. Разрешение для одной мысли не глобализируется.

### Оценки и начальные коэффициенты

Числа ниже — проверяемая гипотеза v1, не вероятность истинности и не научно подтверждённая шкала. Расчёт выполняется кодом; модель не присылает окончательный вес.

E — сила основания: 1.0 прямое недвусмысленное утверждение; 0.6 наблюдаемая авторская правка с ограниченной интерпретацией; 0.3 слабый поведенческий сигнал. Чужие/вымышленные источники отсеиваются до оценки.

n — число независимых групп свидетельств. Для поведенческого обобщения одна мысль = максимум одна группа. Несколько сообщений/версий и retry внутри неё не независимы.

R = 1 - exp(-max(0, n - 1) / 2).

C = 0 без противоречий; существенное неразрешённое противоречие дополнительно блокирует active независимо от численного веса.

D = clamp(0.65 × E + 0.35 × R - 0.50 × C, 0, 1).

U — полезность: 1.0 для прямого влияния на вопросы/сценарий; 0.5 для косвенной связи; 0 для отсутствия продуктовой пользы. Нужен reasonCode и пример влияния. Модель может предложить категорию, код проверяет допустимое значение.

S — устойчивость по типу сведения; A — актуальность по типу и времени. В I04 определить явную таблицу значений и сроков, не назначать единый срок давности прошлому опыту и текущим целям.

M = D × U × (0.60 + 0.25 × S + 0.15 × A).

Важно: одиночное прямое утверждение при этой формуле не достигает 0.70. Поэтому действует отдельный путь: явное актуальное сведение высокой продуктовой полезности или явное общее предпочтение активируется сразу после фильтров; пороги ниже относятся к накопительным выводам. Не заставлять повторять прямую инструкцию.

Для накопительных выводов: M ≥ 0.70 — active; 0.45 ≤ M < 0.70 — candidate; ниже — не сохранять долговременно. Поведенческое обобщение активировать только при минимум трёх независимых мыслях и отсутствии конфликта. Выход из active при M < 0.50; это гистерезис, не две противоречивые границы.

### Бюджеты

- До 20 активных обычных записей и 30 кандидатов на пользователя; не заполнять искусственно.
- Ограничения приватности и использования материала не вытесняются лимитом обычной памяти. Их объединять без ослабления; контролировать отдельным лимитом контекста и безопасным отказом от включения спорного материала.
- Кандидаты без нового независимого основания 30 дней истекают. Значение настраиваемое; исходная переписка не удаляется.
- Семантические дубликаты объединяются без суммирования повторных источников. Отрицание и противоположные предпочтения не объединять как синонимы.
- При переполнении сначала объединить, затем убрать устаревшее, затем оставить наиболее значимое. Детерминированное разрешение равенства весов.
- В вызов обычно 3–7 обычных релевантных записей плюс обязательные применимые ограничения. Ограничить также токены и длину одной записи.
- retrievalPriority = M × relevance, но disputed/недопустимые записи исключаются до ранжирования.

### I03. Состояние мысли и вопросы

Реализовать ThoughtState reducer. Извлекать намерение, позицию, события/основания, локальную аудиторию, границы тезиса, решения и открытые пробелы. Привязывать к версиям исходных материалов. Не требовать одинаковую структуру от истории, личного наблюдения и объяснения.

Планировщик выбирает один полезный пробел, проверяет, не отвечено ли уже, и выдаёт вопрос либо предложение перейти к сценарию. Пропущенные вопросы не повторяются механически. Достаточность не равна числу ходов. Автор может продолжить без ответов на все вопросы.

Если дубль ещё расшифровывается, его содержание не считается известным. Ручные правки сохраняют приоритет. Late response не заменяет более новое состояние.

Приёмка: каждый вопрос связан с реальным пробелом или имеет явную причину уточнения задачи; нет выдуманного случая; повторный ответ закрывает существующий пробел; сценарий не перезаписывается автоматически. Отчёт и ревью.

### I04. Автоматическая память и веса

Реализовать извлечение кандидатов, обязательные фильтры, детерминированную scoring policy v1, дедупликацию, накопление независимых свидетельств, конфликт/коррекцию, бюджеты и истечение кандидатов.

Прямые полезные сведения и предпочтения могут активироваться сразу. Неоднозначность решается conservative defaults: локально, candidate или disputed — без запроса подтверждения памяти. Разрешено задавать вопрос для работы над роликом, но не маскировать под него процедуру одобрения профиля.

Не получать глобальное предпочтение из одной правки или выбора итогового дубля. При наличии финального выбора учитывать только наблюдаемый результат; не объявлять весь текст «идеальным стилем».

Приёмка: повтор одной операции не увеличивает вес; три независимые мысли отличаются от трёх сообщений; одна прямая коррекция заменяет старые свидетельства; лимиты соблюдаются; модель не может присвоить себе произвольный вес; ни один auto-update не требует пользовательского подтверждения. Отчёт и ревью.

### I05. Автоматический портрет и сборка контекста

Удалить обязательные confirm-переходы из профильного процесса и заменить связанные тесты новыми контрактами. Сохранять рабочую ревизию при ошибке/невалидном анализе. Новый профиль может быть частичным; не выдумывать восемь заполненных полей.

Строить детерминированную проекцию памяти в ProfileRevision, используя извлечённые формулировки и источники. Создавать ревизию только при семантическом изменении состава/значений/usage, не при каждом изменении внутреннего веса. Удалённые/устаревшие значения не «восстанавливаются» из старого резюме.

Профильный экран показывает актуальное состояние без кнопки подтверждения; добавить спокойное пояснение об автоматическом учёте ответов. Сброс персонализации остаётся необязательной настройкой, не частью диалога. При сбросе сохранить watermark/tombstone, чтобы старые сообщения не породили ту же память при replay.

Каждый вызов получает snapshot с точными выбранными значениями и версиями. Приоритет: текущий запрос → ручной сценарий → локальные решения/материалы → память → ремесло. Ограничения доступа и использования применяются до этой иерархии и не отменяются паттерном. Текущая локальная задача может переопределить стиль, но не ослабить права доступа.

Приёмка: новое предпочтение меняет следующий подходящий вопрос; неуместные биографические детали не подмешиваются; старая мысль использует новый применимый профиль в новом вызове без переписывания старого snapshot; сброс устойчив к retry. Отчёт и ревью.

### I06. Библиотека ремесла

Сначала версионируемый файл/каталог в репозитории, без векторной БД. Подготовить небольшой стартовый набор только из доступных проверенных исследований. Если корпуса нет, реализовать интерфейс и пустую библиотеку, отметить отсутствие контентной приёмки, не сочинять результаты анализа.

Карточка: id/version, contentMode, applicableGap, mechanism, questionStrategy, prerequisites, contraindications, source reel IDs/fragments, speakerAttribution, duplicateGroup, evidenceStatus. Технические fixtures явно отделить от исследовательских паттернов.

Подбирать 0–4 приёма по режиму/пробелу. Ноль — допустимо. Не заставлять каждый сценарий содержать residual_reality или дерево причин. Чужие формулировки, события и шутки не копируются. Почти дубли не независимые доказательства. Гость/смесь не становятся авторским паттерном без редакторской проверки исследователя (это не подтверждение конечного пользователя). Длинные эфиры обрабатывать отдельно.

Приёмка: source IDs существуют; несовместимый режим исключает паттерн; библиотека может отсутствовать без поломки диалога; snapshot фиксирует использованную версию. Отчёт и ревью.

### I07. Надёжность, расходы и удаление

Связать общий operationId с анализом, изменениями памяти, snapshot и ответом. На apply проверять версии состояния/памяти и sourceWatermark. При гонке не применять старый управляющий результат к новой версии. Не держать DB transaction открытой на время LLM-запроса.

Раздельно учитывать попытки AI и однократное применение продуктового результата: реально повторённый платный вызов не исчезает из расхода. Общий лимит охватывает анализ и генерацию. При недостатке лимита сохранять материал, показывать понятное состояние без потери данных.

Проверить удаление аккаунта/источника: связанная память пересчитывается или исключается, orphan evidence не остаётся, будущие вызовы не используют удалённое. Исторические персональные копии обрабатываются по политике удаления, без фиктивного обещания вечной неизменности.

Приёмка: тесты гонок, retry, падения между commit памяти и ответом, отзыва доступа, превышения лимита, удаления источника и reset; проверка двух пользователей. Отчёт и ревью.

### I08. Сквозная оценка и включение

Прогнать фиксированный набор кейсов и ограниченную live-выборку на доступной модели. Разделить детерминированные тесты правил и оценку смыслового качества; mocks не доказывают качество вопросов. Зафиксировать prompt/model/policy версии и стоимость.

Сравнить базовую помощь без памяти/ремесла с новой на одинаковых материалах: уместность вопроса, сохранение авторской позиции, конкретность, отсутствие выдумок, повторы, ошибочное запоминание. Результаты предъявить ревьюеру, не поручать окончательную приёмку той же модели-генератору.

Приёмка: все критические сценарии таблицы ниже проходят; численные коэффициенты либо подтверждены наблюдениями, либо явно оставлены как калибруемая v1 без заявления об оптимальности. Проверки mobile/desktop на текущих согласованных размерах. Feature flag включает новый путь без потери старых данных; отключение останавливает автоматическое обучение, а не восстанавливает удалённые сведения. Релиз — только после внешнего принятия конкретного SHA.

## 8. Единый отчёт каждого этапа

- BASE_SHA, ветка, commits, HEAD_SHA; не объявлять merge фактом приёмки.
- Изменённые данные/API/UI, обратная совместимость и миграции.
- Сверка перенесённых сущностей/usage/источников, если была миграция.
- Проверки проекта из фактического package.json; существующие lint, typecheck, build, test:reels не обходить и не ослаблять ради зелёного результата.
- Новые значимые integration tests; отдельно реальные AI-проверки и то, что проверено только mocks.
- Примеры: исходный ответ → наблюдение → решение кода → память → следующий вопрос, без реальных секретов.
- Расход, число вызовов, известные ограничения и заблокированные проверки.
- Обновлённые документы: новые решения имеют приоритет над отменённым confirm-flow.
- Вердикт запрашивается у внешнего ревьюера после готового проверяемого результата. Следующий этап не начинать автоматически.
